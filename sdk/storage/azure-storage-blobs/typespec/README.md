# Blob protocol generation

The private protocol client is generated from the BlobStorage TypeSpec
specification pinned in `tsp-location.yaml`. `tspconfig.yaml` enables pipeline
reuse, typed response header models (`includeHeadersInResponse: true`),
and streaming binary responses. Generated files live in `src/generated`,
under `Azure::Storage::Blobs::_detail`.

`src/blobs_protocol.cpp` adapts generated options and results to the existing SDK
models and translates HTTP failures through the Storage error parser. Public
clients retain their transfer logic, retries, service-version policy, and
caller-owned request streams. Downloads and query responses remain streaming.

Batch construction, dispatch, and deferred subresponse parsing remain
handwritten, including the Delete Blob and Set Blob Access Tier subrequests.
These paths retain the existing policy pipelines without calling generated
operations. Ordinary Delete Blob and Set Blob Access Tier calls remain generated.
Flat and hierarchical listing use generated streaming HTTP calls
with the existing XML and Apache Arrow readers. Range requests use the standard
`Range` header directly from the specification; Azure-specific source-range and
range-checksum headers are retained. A private pipeline policy preserves the
remaining Storage header conventions before user policies run.

All public headers, including `inc/azure/storage/blobs/rest_client.hpp`, are
retained for source compatibility. Do not replace them with generated headers
or manually edit generated C++.

## C++ customizations

The pinned specification's `client.tsp` and `Cpp/client.tsp` apply C++-scoped
customizations without changing other languages or the REST API definition.
These inputs are maintained in
[Azure/azure-rest-api-specs#47446](https://github.com/Azure/azure-rest-api-specs/pull/47446);
no package-local TypeSpec overlay is needed:

- Batch operations and typed listing operations are excluded.
- Replacement listing operations expose raw response streams, optional
  delimiters, and the legacy `endBefore` query parameter.
- Already encoded block IDs, delegation keys, XML checksums, and expiry values
  retain their existing representations.
- Metadata uses the `x-ms-meta-` header collection.
- Conditional response headers are nullable where the service may omit them.
  The compatibility adapter still enforces legacy required
  headers when constructing public results.
- Query text settings preserve explicitly empty strings. An empty Parquet
  configuration model preserves the existing XML shape.

## Regeneration

Use a clean checkout or snapshot of
[`Azure/typespec-cpp`](https://github.com/Azure/typespec-cpp) at commit
`7a902b92d515b4c3484fcefce1216336d9718a75`
([Azure/typespec-cpp#585](https://github.com/Azure/typespec-cpp/pull/585)).
This revision includes the default-off response-header option, intrinsic optional
ETags, fixed-precision XML date-times, and streaming binary request/response
support. The unmodified published emitter and unrelated local experiments are not
supported generation inputs.

Build `packages/codegen.cpp` first, then `packages/typespec-cpp`, using their
package manifests. The generation toolchain uses TypeSpec compiler 1.12.0 and
client-generator-core 0.68.4.

Provide the BlobStorage directory from the exact specification revision in
`tsp-location.yaml`. From this package directory, run:

```powershell
.\typespec\generate.ps1 `
  -EmitterPath C:\path\to\typespec-cpp\packages\typespec-cpp `
  -SpecDirectory C:\path\to\azure-rest-api-specs\specification\storage\data-plane\BlobStorage `
  -ClangFormatPath C:\path\to\clang-format-11\clang-format.exe
```

The script stages the pinned service inputs, including `Cpp/client.tsp`, and
generates directly from their `client.tsp`. It formats the five files with
clang-format 11.0.0 in a temporary directory before copying them into the package.
Use `-OutputDirectory` to regenerate elsewhere for comparison. The compatibility
adapter is handwritten and is not regenerated by this command.

After regeneration, build the package, run the credential-free
`BlobsProtocolTest.*` cases, and run all five Storage playback suites, including
Data Lake interoperability. Verify that public headers remain unchanged.
